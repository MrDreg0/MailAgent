Объедини частичные markdown-дайджесты релизов за {{DIGEST_DATE}} в один итоговый markdown-документ.
Убери дубли, сократи шум и оставь только то, что полезно прочитать утром.
Сохрани строго такую структуру:
# Дайджест релизов за {{DIGEST_DATE}}
## Главное
## Релизы
### Продукт или сервис — версия
- ...

Правила:
- Максимум 3 пункта в разделе "Главное".
- Максимум 5 секций в разделе "Релизы".
- Объединяй related entries про один продукт, одну версию или одну волну однотипных security updates.
- Если несколько сервисов обновлены одинаковым security fix в один день, сведи их в один общий блок вроде platform services / security updates.
- Не добавляй source, from, date, ссылки, release notes, docker-образы, пути к файлам, номера задач, эмодзи и служебный шум.
- Не повторяй одинаковые факты в нескольких секциях.
- Если подробностей мало, пиши кратко и честно.
- Предпочитай смысл изменения, а не артефакты поставки. Не делай пункты в разделе "Главное" про ссылки, release notes и docker-образы.
- Если есть версия продукта и отдельно installer той же версии, оставь один объединенный блок.
- Удаляй фразы про "веб-клиент доступен по ссылке", "подробности в release notes", "доступны пакеты/образы/утилиты", если они не описывают суть изменения.
- Если в итоговом тексте осталась только информация про ссылки, портал релизов, release notes или артефакты поставки, сократи ее до простого факта выхода версии либо выброси как шум.
- Если блок про продукт по сути говорит только "вышла новая версия, доступен веб-клиент/ссылка", перепиши его в краткий факт обновления версии без упоминания ссылки, веб-клиента и доступности.
- Не выводи raw snake_case / CamelCase / test-style идентификаторы, имена таблиц, файлов, методов и внутренних классов, если смысл можно передать человеческим языком.
- Даже если во входных частичных дайджестах остались внутренние идентификаторы, перепиши их в понятное описание эффекта, исправления или изменения поведения.
